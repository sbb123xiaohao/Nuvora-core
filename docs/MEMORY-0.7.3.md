# 0.7.3：恢复文件后的堆扩容修复

本轮确认并修复一项 RAM 文件系统内存问题。修改对象是 Nuvora Core；外层 Linux 源码材料没有参与构建或修改。ABI 1、128 KiB 单文件限制、NVSTORE1/NVSTORE2 磁盘格式保持兼容。

## 根因与复现

新建文件从 256 字节容量开始翻倍；但 `fs_import_home` 按快照中的真实文件大小分配，容量不一定是 2 的幂。原 `fs_write` 直接翻倍该容量，可能超过 `NV_FILE_MAX`，即使实际文件没有超限。

例如，恢复一个 131071 字节文件后追加 1 字节，原代码请求 262142 字节，分配器对齐后占用 262144 字节。最终文件只有 131072 字节，却额外占用 128 KiB 堆空间。若仅剩一个 131072 字节空闲块，原代码返回 `-NV_ENOMEM`，尽管该空闲块足够完成这次合法写入。

`tests/fs_memory_test.c` 同时直接包含真实的 `kernel/memory.c` 和 `kernel/fs.c`，通过快照导入创建非整幂容量，再用真实 `kmalloc` 占住其余堆空间。将它与 0.7.2 的 `fs.c` 组合运行，得到：

```text
FAIL restored file growth: size=131071 budget=131072 result=-3 capacity=131071 (maximum 131072)
```

失败记录保存在 `build/x86_64/test-results/fs-memory-before-0.7.2.log`。这是可避免的内存不足和缓冲区浪费；这次复现没有证明越界写或内核崩溃。

## 修复

扩容时将下一步容量限制为 `min(cap * 2, NV_FILE_MAX)`。原有“分配成功后才替换旧缓冲”的流程保留：实际内存不足仍返回错误，并保留文件内容、长度、容量、描述符偏移和堆计数。新缓冲的稀疏区仍清零，删除文件后释放完整分配。

## 验证

- 新增源码夹具覆盖 257、65535、65537、131071 字节恢复文件，每种大小分别在充足内存、恰好 128 KiB 可用、比 128 KiB 少 16 字节的条件下运行，共 12 个场景；检查容量上限、旧内容、稀疏区、失败原子性和全部回收。全部 7 组宿主源码回归通过 GCC UBSan。
- x64 和 i686 均以 32 MiB QEMU 从带有效校验和的磁盘快照启动，再运行 `forge probe file-growth` 的 7 项用户态断言。它验证单字节追加、实际堆占用、完整数据、拒绝超限写入及删除回收。
- 完整 QEMU 矩阵为 x64 53 组、i686 42 组。常规 probe 数量仍为每轮 130/123 项；新增的 7 项属于独立快照场景，未混入常规 probe 数字。
- BIOS/UEFI 启动、内核栈保护、物理页耗尽、进程与页表回收、USB 热插拔等现有检查继续通过。源码、内核、用户程序、EFI 和 ISO 均绑定执行指纹，打包时核对。

复现命令见 [TESTING.md](TESTING.md)。`--phase memory` 和 `--phase storage` 均包含新场景。QEMU TCG 的 SSE #XM 递交仍明确标记 SKIP；没有实体硬件或长期稳定性认证。
