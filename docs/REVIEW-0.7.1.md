# Nuvora 0.7.1 修复记录

此文保留 0.7.1 的历史结果；当前包为 0.7.2，构建目录日志对应本轮版本。后续内存修复见 [MEMORY-0.7.2.md](MEMORY-0.7.2.md)。

修复范围为原包中的 `nuvora-core-0.6.0/` 子项目；原包内部版本标识为 0.7.0，本次统一为 0.7.1。外层 Linux 材料不参与 Nuvora 的构建或链接，修复包保留其原始字节内容。Linux 压缩包 SHA-256：`039aef84f2b0994aeda3f4fcfc3d02ec9d7a9bbb9020ea264c43f446c860f606`。

## 已修复的问题

| 范围 | 原因与修复 |
| --- | --- |
| x64 大内存 | 32 位对齐掩码截断高地址；统一操作数宽度。用户 1–2 GiB 映射会替换对应恒等映射，新增 512 GiB 基址的 supervisor 物理别名，明确物理地址和 CPU 指针的转换。 |
| 页与 DMA | 页表、拷贝和 USB 对物理地址的直接解引用改用映射指针；回收时屏蔽 NX 位；内核栈/MMIO 窗口覆盖的完整物理范围保留。 |
| UEFI | 补全 EFI 服务表缺少的 SignalEvent，修正 ELF/PE32+ 字段与重定位；读取文件前 rewind，支持短读；写入前验证全部段和入口；刷新退出服务重试内存图，检查固件内存所有权，用自有栈交接。 |
| 固定加载区 | x64 内核堆原占静态 BSS，跨入 OVMF 的 ACPI NVS。改在分页初始化后从可用 RAM 分配并永久保留，防止自检或普通释放误回收。 |
| 数据保护 | NVSTORE 签名与版本一致性、几何溢出、ATA 容量/flush 检查；有效快照因资源不足无法恢复时禁止后续覆盖，缓冲服从小槽容量，扇区尾部清零。 |
| 工程与启动 | 修复 i686 链接、PE/ESP 生成和构建失败被忽略；ESP 原子替换；OVMF CODE/VARS、q35 ESP 接口、启动器内存参数；源码与产物指纹阻止测试后变更混入发布包。 |

## 实际验证

2026-09-18，GCC 13.3.0、GNU ld 2.42、QEMU 8.2.2 TCG。

| 验证 | 结果 |
| --- | --- |
| x64 完整矩阵 | 51 组通过；每次用户 probe 126 项成功 |
| i686 完整矩阵 | 41 组通过；每次用户 probe 121 项成功 |
| 新增源码夹具 | 地址、ATA、快照、UEFI 共 4 组通过，UBSan 开启 |
| RAM | 两架构 32/64/128/256 MiB；x64 另有 1 GiB 和 5 GiB，跨 4 GiB 边界 |
| 启动 | 两架构 BIOS ISO；x64 OVMF 直接启动、保存恢复和独立 UEFI 光驱 ISO |
| 磁盘 | 4 TiB 稀疏镜像容量识别与低 LBA 快照往返；高 LBA 端口顺序另由源码夹具验证 |
| USB | 66 次根端口插拔、事件/命令环回绕、Hub、键盘与页面回收 |

每次 probe 仍有 1 项 SSE #XM 递交检查明确标记 SKIP；其余成功断言不表示该硬件异常已验证。没有进行实体硬件认证。完整逐项结果位于 `build/x86_64/test-results/RESULTS.md` 与 `build/i686/test-results/RESULTS.md`，复现说明见 [TESTING.md](TESTING.md)。

## 容量边界

宿主有大量资源不代表当前内核没有容量限制。本轮修复寻址和数据保护，没有通过修改常量伪装无限容量。

| 资源 | 当前实现 |
| --- | --- |
| 物理 RAM 管理 | x64 64 GiB；i686 192 MiB，实际矩阵最高 5 GiB |
| 用户地址空间 | 1–2 GiB 窗口；每进程堆 4 MiB |
| 内核堆 | 8 MiB |
| 文件系统 | 128 个节点；普通文件最大 128 KiB |
| 快照 | 单份最多 16 MiB，实际缓冲受 RAM 和槽容量约束 |
| ATA / 镜像 | LBA48、512 字节扇区，脚本不超过 2^48 扇区；扩大镜像不扩大文件系统或快照容量 |

解压后进入 `nuvora-core-0.7.1/`，运行 `python3 start.py --memory 5120`；UEFI 加 `--uefi`，需要安装 QEMU 与 OVMF。发布包包含源码、预编译 ELF、BIOS/UEFI ISO、ESP、执行日志及 SHA256SUMS，不包含临时测试磁盘。
